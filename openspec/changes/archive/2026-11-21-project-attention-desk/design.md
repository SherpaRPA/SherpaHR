# Design

## Context

См. [proposal.md](proposal.md) и [спецификацию](specs/project-attention/spec.md). `Application.php` проверяет доступ к проектам через `project_members`, а `writable()` запрещает запись в архив. Карточка находится в `AppComponent`, но сейчас форма использует выбранный проект. Таблица `comments` уже содержит все поля для записи; существующий smoke-тест ожидает `201`.

## Goals / Non-Goals

**Goals:** единый серверный расчёт очереди, один путь чтения и записи карточки, совместимость с имеющейся SQLite.

**Non-Goals:** выделение нового сервиса, миграция БД, изменения схемы прав или фоновые обновления.

## Decisions

1. **Агрегация на сервере.** Добавить `GET /api/attention`, возвращающий в стандартной обёртке массив строк с задачей (`id`, `title`, `project_id`, `assignee_id`, `due_at`), именем проекта, массивом кодов причин и необязательным контекстом `latest_comment` (`author`, `excerpt`). Использовать один запрос SQLite с ограничениями по членству, `owner_id`, архиву и статусу. Дату сравнивать с одним UTC-снимком времени на запрос; определять причины и сортировку в одном месте. Для последнего комментария использовать порядок `id DESC` (тот же порядок добавления, что и в карточке), с существующим индексом `(task_id, id)`; отдавать до 160 символов Unicode с многоточием при обрезке. Это предпочтительнее клиентской загрузки списка каждого проекта и карточек каждой задачи: меньше запросов, а права и серверное время не зависят от UI.
2. **Один редактор, две точки входа.** Хранить режим «обзор / проект» отдельно от состояния карточки. При чтении или правке задачи разрешать проект карточки по `project_id` из деталей и списку доступных проектов; для создания использовать явно открытый проект. Не делать скрытого переключения проекта, иначе пользователь потеряет очередь. После записи обновлять активную очередь отдельным запросом, не сбрасывая карточку и не подменяя успешное сохранение ошибкой перечитывания; при сбое показывать ошибку обновления и кнопку повтора. На смене пользователя очищать обзор и карточку синхронно, игнорировать ответы предыдущего поколения. На узком экране открытие карточки из очереди должно переводить фокус к её заголовку: сейчас панель расположена после основного контента.
3. **Восстановить существующий контракт записи.** В `POST /api/tasks/{id}/comments` сохранить результат серверной валидации, проставить автора и время на сервере и вернуть сохранённую строку с `author` в формате чтения карточки. Не обновлять версию задачи: обсуждение и редактируемые поля независимы. Сохранить существующие проверки перед записью. В UI убрать расхождение `maxlength=2000` с контрактом API, считать байты UTF-8 и оставлять введённый текст при отказе. Текст в карточке и очереди выводить интерполяцией, без HTML. Из списка проекта убрать соединение с `users`, поскольку оно не используется для вывода и исключает `NULL`.

## Risks / Trade-offs

- Свободный текст может содержать просьбу без формального сигнала → не обещать полноту очереди и не выдавать последний комментарий за причину.
- Просрочка меняется со временем, а обзор — снимок → пересчитывать при входе, переключении человека, ручном обновлении и успешной записи из обзора; не добавлять таймер или polling.
- Демо-сроки сдвигаются только при создании БД → для проверок выбирать даты относительно серверного времени; для точной границы использовать фиксированное время в тесте логики, а не ожидания по таймеру.

## Migration Plan

Пересобрать frontend и развернуть вместе с обновлённым API. Существующую SQLite и Docker volume сохранить; миграций и пересоздания демо-данных не требуется. Откат версии приложения не требует отката данных, а сохранённые комментарии останутся доступны для чтения.
