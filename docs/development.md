# Разработка

Frontend: Angular 22, standalone-компоненты, signals и FormsModule.
Backend: PHP 8.4+, PDO SQLite, JSON API. Зависимостей Composer нет.
Схема создаётся `backend/src/Database.php` из `backend/schema.sql` при первом
обращении; данные хранятся в `var/project-desk.sqlite`.

## Локально без Docker

Нужны PHP с `pdo_sqlite`, Node 22.23.3+ и npm. В двух терминалах:

```bash
# Из корня репозитория
php -S 127.0.0.1:8098 backend/router.php
```

```bash
cd frontend
npm ci
npm start
```

Frontend доступен на http://localhost:4200, `/api` проксируется на порт 8098.

```bash
php backend/tests/smoke.php
cd frontend
npm run build
```

Тест API поднимает отдельный сервер и временную SQLite, затем удаляет её.
Smoke проверяет добавление комментариев, включая авторство, валидацию
и ограничения доступа.
`DB_PATH` позволяет указать отдельную БД; `SEED_NOW=2026-11-11T08:00:00Z`
задаёт исходную дату только при создании новой БД. Текущее серверное время
возвращается в `/api/context`; это не остановленные часы приложения.

## Docker

`docker compose up --build -d --wait` собирает frontend и отдаёт его тем же PHP
сервером, что обслуживает API. Это сервер для локального тестового задания;
production web-сервер и настоящая аутентификация в комплект не входят.

`make up`, `make test`, `make down` — сокращения команд Compose.
`docker compose build` пересобирает код; существующая БД остаётся в volume.

На стадии сборки frontend выполняются `npm test`, `npm run typecheck` и
`npm run build`. Новых зависимостей для тестов нет: используется `node:test`
и имеющийся TypeScript. `frontend/tests/app.test.cjs` проверяет реальные методы
компонента с подменённым HTTP и Angular signals: переход в карточку, смену
пользователя, запоздалые ответы, ошибку/повтор загрузки и сохранение черновика.
Это проверки состояния компонента; они не заменяют проверку DOM в браузере.
Smoke API также проверяет обзор внимания и доступ разных пользователей.
Регрессии включают завершение сохранения после возврата в обзор и смену
пользователя при незавершённом запросе. При открытии из обзора фокус после
отрисовки переходит в карточку; отменённый переход фокус не перехватывает.

## Ручная проверка обзора

1. После пересборки откройте приложение от Анны: первым показан обзор.
2. Проверьте причины, проект, исполнителя и срок. Архивный вебинар, проект
   аналитика и готовые задачи не должны появляться в обзоре Анны.
3. Откройте задачу из обзора: выбран её проект, доступны полная переписка,
   добавление комментария и изменение задачи.
4. Снимите блокировку и задайте будущий срок либо завершите задачу. Вернитесь
   в обзор: она больше не подходит критериям. Для проверки без изменения данных
   можно ограничиться переходом в карточку и возвратом.
5. Переключитесь на Веру: список должен пересчитаться по её доступу. Вернитесь
   к Анне; данные предыдущего пользователя не должны остаться.
6. Кнопка «Обновить обзор» показывает новый снимок серверного времени.
   При сетевой ошибке есть явное сообщение и повтор загрузки.

## Структура

- `frontend/src/app.*` — текущие экраны проектов и карточка задачи.
- `frontend/src/api.ts`, `models.ts` — клиент API и типы.
- `backend/router.php` — API и выдача собранного frontend.
- `backend/src/Application.php` — маршруты, проверки доступа и изменения данных.
- `backend/src/Database.php`, `schema.sql` — создание БД и демонстрационный набор.
- `backend/tests/smoke.php` — проверка существующих сценариев API.

Ошибки изменений API возвращаются с HTTP-статусом и полем `error`.
Конфликт версии при редактировании — 409: откройте задачу заново.
Собранный frontend, node_modules, БД и секреты игнорируются Git.
